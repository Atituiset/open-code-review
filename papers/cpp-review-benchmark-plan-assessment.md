# C/C++ Code Review 评测集建设方案：评估文档

> 评估对象：《C/C++ Code Review 评测集建设：深度调研报告》（`papers/cpp-review-benchmark-research.md`）第 3 节的三层金字塔方案。
> 日期：2026-08-14。结论先行：**方案可行，建议按三期执行，一期 12 周，核心风险在标注资源而非技术管线。**

## 1. 评估结论摘要

| 维度 | 评估 | 依据 |
|---|---|---|
| 技术可行性 | ✅ 高 | 种子池管线（CVE→commit→diff）已有三个开源实现可参照（CVEfixes/DiverseVul/SecVulEval），无技术盲区 |
| 数据可得性 | ✅ 高 | CVEfixes/DiverseVul/SecVulEval 均公开，合计覆盖 1999–2024、超 7 千 C/C++ 修复 commit |
| 标注可行性 | ⚠️ 中 | 需要 2 名资深 C/C++ 工程师投入约 3~4 周，是最大成本项和最大风险项 |
| 差异化价值 | ✅ 高 | 业内无 PR 级 C/C++ review 评测集（调研已证实），补空白 |
| 主要限制 | ⚠️ 一期只能覆盖安全类问题 | 种子源全部是 CVE 修复数据，非安全类 review 问题（可读性、可维护性）无现成种子池 |

## 2. 范围界定（防 scope 蔓延）

**一期做**：C/C++ 安全类问题的 PR 级 review 评测集（~100 个 PR、~300 条 golden comments）+ 评估协议 + 基线跑分。

**一期不做**（明确排除，避免半途膨胀）：
- 非安全类问题（可读性/可维护性/架构）——需要另一条种子线（真实 code review 评论挖掘），二期再说；
- online 持续采样轨道（Martian 双轨中的 online 轨）——一期用"2023 年后 CVE + test 集私有"对冲泄漏即可；
- 除 C/C++ 外的语言；
- 工具方的训练数据生成（本评测集只做评估，不做 SFT/DPO 数据）。

## 3. 工作量与成本估算

### 3.1 人力（一期，12 周）

| 环节 | 角色 | 投入 | 说明 |
|---|---|---|---|
| L1 种子池管线 | 数据工程师 ×1 | 3 周 | 合并三源、OneFunc/NVDCheck 初筛、归一化去重、时间过滤；均有开源参照 |
| L2 标注试点（20 PR） | 资深 C/C++ 工程师 ×2 | 1 周 | 口径校准、标注指南定稿、共识率基线测量 |
| L2 全量标注（100 PR） | 同上 ×2 | 3~4 周 | 按每 PR 独立审 30~60 分钟估算，合计约 150 人时 + 仲裁约 20 人时 |
| L2 质量审计 | 第三方安全专家 ×1 | 1 周 | 每 CWE 类抽 50 样本复核（PrimeVul 标准），出标签正确率报告 |
| L3 校准层 | 数据工程师 | 0.5 周 | CASTLE 子集接入，基本是现成数据 |
| 评估 harness + 基线 | 评测工程师 ×1 | 2 周 | 两层匹配（tag 规则 + 轻量 LLM 语义判等）、按 CWE 分层报表、跑 4~6 个基线 |
| **合计** | | **约 10~12 人周** | 瓶颈是 2 名资深工程师的 3~4 周 |

### 3.2 资金（量级估算）

- 标注人力：按资深安全工程师市场价，约 **15~25 万元**（国内）或等值外包；这是总成本的 80%+。
- LLM API（候选问题生成、rationale 改写辅助、judge）：数千元量级，可忽略。
- 基础设施：GitHub 克隆 + SQLite/JSON 存储，无特殊需求。

### 3.3 关键判断

成本结构决定了：**宁可把规模从 100 PR 缩到 60 PR，也不能降级标注协议**。Devign 的教训（号称专家标注、实测 24% 正确率）证明粗协议的人工标注比自动标注更有害——它给数据集披上不值得的信任外衣。

## 4. 里程碑计划（12 周）

| 里程碑 | 周 | 交付物 | 验收标准 |
|---|---|---|---|
| M1 种子池就绪 | W3 | L1 管线 + 候选 commit 清单（~500 条） | 抽 50 条人工复核初筛准确率 ≥85%（对标 PrimeVul OneFunc/NVDCheck 的 86%/92%） |
| M2 标注试点 | W5 | 标注指南 v1 + 20 PR 双标结果 | 报告共识率与分歧分类；共识率 <50% 则修订指南再试点，不进入全量 |
| M3 主评测集 | W9 | 100 PR 全量标注 + 共识集 + hard case 子集 | 每条 golden comment 三维（CWE/函数/锚点）一致；审计标签正确率 ≥90% |
| M4 发布 | W12 | 评测 harness + dev/test 时间切分 + 基线报告 | 基线排序符合预期（见 §6）；结果可一键复现 |

**缓冲**：W9 与 W12 之间留 1 周机动；若 M2 共识率不达标需返工，优先砍 PR 数量保标注质量。

## 5. 风险评估矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| 标注者招募难（资深 C/C++ 安全工程师稀缺） | 高 | 高 | 提前 4 周锁定人选；备选：与高校安全实验室合作（Devign 的 4 名安全研究员模式）；最终兜底：缩减至 60 PR |
| 双人共识率过低（C/C++ UB/并发问题天然分歧大） | 中 | 高 | M2 试点先测共识率；分歧项进 hard case 子集而非丢弃（调研方案已含此设计）；标注指南用 Devign 公开子集做练兵 |
| 2023 年后 C/C++ CVE 数量不足 | 中 | 中 | SecVulEval 已覆盖至 2024 可直接取用；不足时放宽至 2022 年 + 加 canary 样本检测污染 |
| 训练数据泄漏（被测模型见过 CVE 原文） | 中 | 中 | test 集不公开，仅公开 dev 集；定期轮换；记录每个 CVE 的公开日期与主流模型训练截止日对照 |
| judge LLM 版本漂移导致历史分数不可比 | 中 | 低 | 固定 judge 模型版本写入结果元数据；保留 10% 人工抽检通道校准 judge |
| 修复 commit 的 diff ≠ 真实 PR 形态（真实 PR 含无关改动、多 commit） | 中 | 中 | 接受偏差并写入文档"已知限制"；二期引入真实 PR 采样对照 |
| CWE 分布头重脚轻（内存类占大头） | 高 | 低 | 分层采样时强制配额，尾部 CWE 保底样本数 |

## 6. 验收标准（怎么算建成）

1. **数据质量**：第三方审计标签正确率 ≥90%（PrimeVul 的 NVDCheck 水平）；发布审计报告原文。
2. **防泄漏**：dev/test 按 commit 时间序切分；同 commit 不跨集；全库归一化去重后重复率 <1%（对标：现有数据集 3.3%~18.9%）。
3. **区分度**：基线跑分应呈现预期排序——静态分析器（Clang SA/Infer）precision 高 recall 低，通用 LLM recall 高 precision 低，专业 review 工具居中。若所有基线分数挤在一起，说明评测集区分度不足，M4 不通过。
4. **可复现**：从种子池到跑分全链路脚本化，`README` 一条命令复现基线表。
5. **文档**：标注指南、已知限制（函数级→PR 级偏差、安全类限定）、引用格式齐备。

## 7. 备选方案对比

| 方案 | 周期 | 成本 | 质量风险 | 结论 |
|---|---|---|---|---|
| **A. 三层自建（调研报告方案）** | 12 周 | ~10-12 人周 | 低（多重质控） | ✅ 推荐 |
| B. 直接改造 PrimeVul 5,480 对配对数据 | 4 周 | ~3 人周 | 高：函数级、无 PR 语境、无 review 风格 rationale，只是"漏洞检测集 v2"，不是 review 评测集 | ❌ 不满足目标形态，但可作为 L1 种子池的现成输入（已纳入方案 A） |
| C. LLM 合成 + 轻人工抽检 | 3 周 | ~2 人周 | 极高：重蹈 CQS 论文自报的偏差（ground truth 由被测模型生成、recall 分母不全），且 SecVulEval 实测 LLM 产出需人工复核（82.98% 准确率） | ❌ 仅可用于辅助工序（rationale 改写草稿），不可作为主流程 |

## 8. 决策点（需要拍板的事项）

1. **标注资源来源**：内部资深工程师 / 外部安全团队 / 高校合作？——决定成本与周期，建议启动前先确认。
2. **规模目标**：100 PR（标准）还是 60 PR（保守）？——建议按 100 规划、按 60 保底。
3. **发布策略**：test 集私有的开放程度（公开 dev + 托管 test 跑分服务，还是全公开）？——影响防泄漏强度与社区采纳度。
4. **二期方向**：是否扩展到非安全类 review 问题？——一期数据管线可复用约 70%，但种子源要新建（真实 review 评论挖掘，参考 CQS 的 6000 diff 筛选管线）。
